 1. DO I NEED TO RUN ANY QUERY?
================================================================================

YES - exactly one file, and only once.

    supabase/APPLY_ALL_WHOLESALE_COMPLETE.sql

How to run it:
    1. Supabase Dashboard -> Database -> Backups -> take a backup.
    2. Dashboard -> SQL Editor -> paste the whole file -> Run.
    3. Confirm the 16-row table at the end reads OK on every line.
       "B. supplier drug licence" may read SKIPPED (expected) if the
       suppliers table is absent; that is fine and is explained in the file.

It is safe to run more than once. The whole file is one transaction, so a
failure rolls everything back, and every step is guarded, so a second run is a
no-op rather than an error. Verified by running it twice against the same
database.

NOTHING ELSE needs to be run. There are no follow-up queries, no data fixes and
no backfills.

After running it, do these two things in the app:
    * Settings -> Tax & Currency -> turn on Wholesale Mode
      (only appears on an account whose plan is wholesale_monthly/annual)
    * Settings -> Store Information -> fill in FSSAI number, Drug License
      Form (20B / 21B / 20G) and Drug License validity date.
      Wholesale invoices omit these rather than printing blanks until set.

================================================================================
 3. THE ONE CHANGE MADE AS A RESULT OF TESTING
================================================================================

Finding : invoice_sequences had row-level security and a policy, but no
          explicit GRANT. The table therefore depended on the project's
          default privileges being configured as expected.

Impact  : none in practice. The app never reads that table directly; it only
          calls next_invoice_number(), which is SECURITY DEFINER and so runs
          as the owner regardless of the caller's grants. The test only caught
          it because it queried the table directly.

Change  : an explicit grant was added, so the behaviour no longer depends on
          project defaults:

            GRANT SELECT, INSERT, UPDATE ON public.invoice_sequences
              TO authenticated;

          Deliberately no DELETE. Removing a counter row would reset the
          invoice series, which is the one thing Rule 46 numbering must never
          allow.

This is already inside APPLY_ALL_WHOLESALE_COMPLETE.sql. No separate query.


================================================================================
 4. THINGS THAT LOOKED LIKE BUGS AND WERE NOT
================================================================================

Recorded so they are not "fixed" later by mistake.

a) Three tests failed on the first run, and one errored. All four were defects
   in my test harness, not in the application:
     - the harness had not granted USAGE on the auth schema to the
       `authenticated` role, which Supabase does grant. auth.uid() therefore
       failed the moment a test switched role, making two valid inserts look
       rejected.
     - the duplicate-counter check grouped by (series, fy) instead of
       (account_id, series, fy), so two tenants legitimately holding
       WS/26-27 looked like a duplicate.
   Both were fixed in the harness and all tests then passed. No application
   code was changed on account of them.

b) src/pages/Suppliers.tsx line 555 contains a U+FEFF character:
       new Blob(['﻿' + csv], { type: 'text/csv;charset=utf-8;' })
   This is deliberate. It is a byte-order mark prepended to the CSV export so
   Excel opens it as UTF-8. Removing it would cause the mangling it prevents.

c) src/pages/PrintBill.tsx contains <td>&nbsp;</td>. That is a spacer cell in
   the invoice table and renders correctly.
